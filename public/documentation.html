AgroFlux Studio

L'outil visuel qui conçoit, valide et publie le parcours de navigation audio de l'application mobile AgroFlux Bénin — un flow JSON qui fait office de contrat officiel pour le backend et l'application Flutter.

React 19 + TypeScript React Flow Vite 8 Tailwind CSS 4 Vitest

À quoi sert ce projet ?

AgroFlux Bénin est une plateforme qui aide les producteurs et revendeurs agricoles du Bénin à accéder aux informations de marché (prix, calendriers d'animation, disponibilité des produits) via une application mobile pilotée par la voix, en français et en langues locales (Fon, Yoruba, Dendi, Adja...). L'application ne contient aucune logique de navigation codée en dur : elle exécute un fichier flow.json qui décrit chaque écran, chaque question posée à l'oral, chaque option, chaque appel API et chaque ressource audio/image nécessaire.

AgroFlux Studio — ce projet — est l'éditeur visuel de ce flow.json. Il permet de dessiner le parcours sous forme de graphe, de le valider automatiquement, de gérer les variables et ressources multilingues, puis de produire un dossier complet (contrat + ressources) prêt à être consommé par le backend et l'application Flutter — sans jamais toucher au code de ces deux applications.

Idée centrale Le Studio ne se contente pas d'éditer un fichier : il définit le contrat officiel entre trois systèmes (Studio, backend, Flutter). Toute route API, tout format de ressource, toute langue supportée passe par ce que le Studio génère.

Pipeline de travail

Le travail dans le Studio suit toujours à peu près le même enchaînement :

1. ConcevoirGraphe, variables, ressources
→
2. ValiderErreurs, avertissements, contrat
→
3. RessourcesScanner le dossier réel
→
4. BuildVérifier/itérer en local
→
5. PublierDossier propre final

Les étapes 3 à 5 se trouvent dans le panneau Studio (voir plus bas) et ont besoin d'un navigateur Chrome, Edge ou Opera (accès réel au disque).

Types de nœuds

Un flow est un graphe de nœuds reliés entre eux. Chaque nœud a un type, qui détermine ses champs et son rôle dans la conversation. Un seul point d'entrée (entry) démarre le parcours.

TypeCouleurRôleChamps propres
ROOT Indigo Menu principal : liste d'options, chacune menant à un autre nœud. options: [{ id, next }]
GRID Cyan Présente les valeurs d'une variable comme choix (ex. liste des produits). options_source, set, next, can_choix_all, controle_active
PRE_FILTER Ambre Filtre interne : réduit une liste à l'aide d'un HashMap, sans poser de question à l'utilisateur. cle, filtre_source, next, can_choix_all, controle_active
RESULT Rose Nœud terminal : affiche la réponse d'un appel API (le flow s'arrête ici). data_source: { endpoint, method, params }, response_examples
CALENDRIER Violet Sélecteur de date/période spécialisé. periode (jours), cadran (passé/centrer/future), next

Tous les types de nœuds partagent aussi ces champs communs :

  • audio — une séquence audio jouée à l'arrivée sur ce nœud (voir Éditer un nœud).
  • comment — note libre pour les concepteurs du flow, sans effet fonctionnel.
  • json_response_contrat — un exemple JSON du contrat de réponse attendu pour ce nœud (documentation, validé comme JSON mais jamais interprété).
Cul-de-sac Un nœud grid, calendrier ou pre_filter doit toujours avoir un next. S'il n'en a pas, la validation le signale comme un cul-de-sac (avertissement). Seul result est terminal par nature.

Variables & HashMaps

Variables

Une variable est une liste réutilisable de valeurs (ex. produits: ["mais", "soja"]). Un nœud grid présente ces valeurs comme options (options_source) et peut mémoriser le choix de l'utilisateur dans une autre variable (set), réutilisable plus loin dans le flow (par exemple dans les params d'un nœud result).

HashMaps

Un HashMap est une structure clé → liste de valeurs (ex. marche_par_departement: { oueme: ["ouando", "bonou"], plateau: ["takon"] } }). Il sert à filtrer une liste en fonction d'une clé choisie ailleurs dans le flow — c'est le rôle du nœud pre_filter : il prend une variable contenant la clé (cle) et un HashMap (filtre_source), et restreint silencieusement les valeurs disponibles pour la suite du parcours.

États actif / inactif

Chaque valeur de variable et chaque clé/valeur de HashMap peut être marquée inactive sans jamais être supprimée. C'est une couche à part (active_overrides) qui ne modifie ni variables ni hashmaps : elle ne liste que les exceptions inactives, tout le reste est actif par défaut.

Le Studio montre toujours tout Marquer une valeur inactive ne la masque jamais dans le Studio (Gestionnaire de Variables / HashMaps) : pendant la phase pilote, l'intégralité des variables et HashMaps reste développée et visible ici. L'état actif/inactif n'est qu'une donnée transmise — c'est l'application mobile et le backend qui décident, à l'exécution, d'afficher ou non une option en fonction de cette donnée.

Dans le Gestionnaire de Variables, chaque valeur affiche une icône œil cliquable (👁 actif / 🚫 inactif). Dans le Gestionnaire de HashMaps, la même icône existe à la fois sur chaque clé (catégorie entière) et sur chaque valeur de sa liste. Désactiver une clé désactive automatiquement toutes ses valeurs en cascade, même celles non marquées individuellement.

Supprimer une valeur, une clé ou une variable/HashMap entière nettoie automatiquement son exception dans active_overrides — aucune action manuelle requise. Une ressource (audio/image) reste générée pour une valeur inactive : elle pourra être réactivée plus tard sans qu'il manque de fichier.

can_choix_all / controle_active (nœuds GRID et PRE_FILTER)

Deux cases à cocher, propres à chaque nœud grid et pre_filter :

  • can_choix_all — « Autoriser le choix « Tout » » : l'application mobile doit proposer, en plus de la liste, une option pour tout sélectionner.
  • controle_active — « N'afficher que les options actives » : ce nœud précis doit filtrer sa liste selon active_overrides. Décoché (par défaut), le nœud affiche toutes les valeurs, actives ou non, comme avant l'introduction de cette fonctionnalité.
Décision prise nœud par nœud Les deux cases sont décochées par défaut sur tout nœud, existant ou nouveau. Rien ne change tant qu'un concepteur de flow ne les active pas explicitement sur un nœud précis.

Langues

Le flow déclare une liste de langues actives (languages: string[]), éditable librement (voir Paramètres du Flow) — aucune langue n'est figée dans le code du Studio. Par défaut :

fr (référence/débogage), fon, yoruba, dendi, adja.

Seul l'audio dépend de la langue Une image ne dépend jamais de la langue de navigation (une photo de maïs reste la même quel que soit l'idiome parlé) — elle n'est donc jamais dupliquée par langue. Voir la convention de chemin ci-dessous.

Ressources (audio & image)

Pour chaque valeur de variable/HashMap, le Studio calcule automatiquement les chemins de ressources attendus, selon une convention fixe : 

audio/{langue}/{dossier}/{valeur}.{format}          — une entrée PAR langue déclarée
audio/{langue}/{dossier}/{clé}/{valeur}.{format}     — pour un HashMap

images/{dossier}/{valeur}.{format}                   — une seule entrée, jamais par langue
images/{dossier}/{clé}/{valeur}.{format}             — pour un HashMap

Exemple concret avec la variable produits: ["mais"] et les langues fon/yoruba :

audio/fon/produits/mais.mp3
audio/yoruba/produits/mais.mp3
images/produits/mais.jpeg

Le dossier associé à chaque variable/HashMap est configurable dans Mapping Audio & Image ; le format (mp3/wav/ogg/m4a pour l'audio, jpeg/jpg/png/webp pour l'image) y est réglé globalement.

Contrats Backend

Chaque nœud result déclare une data_source : un endpoint (chemin plat, sans placeholder), une method HTTP (GET/POST/PUT/DELETE, POST par défaut si absente) et une liste de params. Convention fixée avec le backend : l'application Flutter empaquette ces paramètres tels quels dans un corps JSON — jamais dans l'URL. 

// Nœud "result" :
"data_source": { "endpoint": "api/app/acheter_produit", "method": "POST", "params": ["produit", "departement"] }

// Flutter envoie :
POST api/app/acheter_produit
{ "produit": "mais", "departement": "zou" }

Le Studio dérive automatiquement de tout le flow un Contrat Backend : la liste consolidée de toutes les routes à implémenter, avec méthode, paramètres et un exemple de réponse — voir Validation du flow.

La barre d'outils, toujours visible en haut de l'écran, regroupe les actions globales :

Guide d'utilisation — Le canevas

  • Zoom : molette de la souris (ou les boutons +/− en bas à gauche).
  • Déplacement : clic-glissé sur le fond, ou molette (pan).
  • Sélection multiple : glisser un rectangle de sélection sur le fond.
  • Sélectionner un nœud : cliquer dessus — ouvre l'éditeur de nœud à droite.
  • Relier deux nœuds : cliquer-glisser depuis le point (handle) en bas d'un nœud vers le point en haut d'un autre.
  • Mini-carte : en bas à droite, colorée par type de nœud, pour naviguer sur un grand flow.

Les liens d'un nœud root sont étiquetés par l'identifiant de l'option ; les autres liens (next) sont de simples flèches.

Guide d'utilisation — Éditer un nœud

Cliquer sur un nœud ouvre un panneau à droite avec les sections suivantes :

Général (tous les types)

  • ID — lecture seule (l'identifiant du nœud).
  • Type de Nœud — changer de type régénère une structure propre pour le nouveau type (les champs incompatibles sont perdus), en conservant l'audio, le commentaire et le contrat de réponse déjà saisis.
  • Configuration Audio (Séquence) :
    • ID unique de l'audio (key) — doit être unique dans tout le flow (la validation le vérifie).
    • Séquence d'audios — liste ordonnée de chemins ou de variables entre accolades, ex. {'{'}produit{'}'} ou {'{'}prix:1000{'}'} pour un formatage spécifique.
    • Fallback — audio joué si un élément de la séquence est introuvable.
  • Commentaire / Documentation — note libre, sans effet fonctionnel.
  • Contrat de Réponse Backend (JSON) — un exemple JSON, validé syntaxiquement (mais jamais interprété) lors de la validation.

Champs spécifiques par type

TypeChamps additionnels
CALENDRIERPériode (jours), Cadran (passé / centrer / future).
GRIDSource des options (variable), Variable de stockage (Set), Autoriser le choix « Tout », N'afficher que les options actives.
RESULTMéthode HTTP + Endpoint, Paramètres (séparés par virgule), Exemples de réponses (backend) — ajout/suppression libre d'exemples JSON.
PRE_FILTERVariable de Clé (Filtre), Source du HashMap (filtre_source), Autoriser le choix « Tout », N'afficher que les options actives.
ROOTOptions du menu — chacune avec un identifiant et un nœud suivant.
GRID / CALENDRIER / PRE_FILTERNœud Suivant (Next) — un seul lien de sortie.
Astuce Pour result, vider entièrement le champ Paramètres donne une liste vide (avertissement "probable oubli"), pas une erreur — une virgule en fin de saisie reste affichée normalement pendant que vous tapez le paramètre suivant.

Détail de can_choix_all et controle_active (GRID / PRE_FILTER) : voir États actif / inactif.

Guide d'utilisation — Gestionnaire de Variables

Accessible via Données ▾ → Variables.

  1. Tapez un nom dans le champ de gauche (ex. produits) puis cliquez sur + pour créer la variable.
  2. Cliquez sur son nom pour voir ses valeurs à droite ; tapez une valeur puis Entrée pour l'ajouter.
  3. Cliquez sur l'icône œil d'une valeur pour basculer son état actif/inactif (voir États actif / inactif) — une valeur inactive apparaît barrée et grisée.
  4. Retirez une valeur avec le × à côté d'elle.
  5. Supprimez toute la variable avec l'icône corbeille — refusé si elle est encore utilisée par un nœud (options_source ou set).

Guide d'utilisation — Gestionnaire de HashMaps

Accessible via Données ▾ → HashMaps.

  1. Créez un HashMap en lui donnant un nom (ex. marche_par_departement).
  2. Sélectionnez-le dans la liste de gauche pour voir son contenu.
  3. Ajoutez une clé (ex. oueme) via le champ en haut à droite.
  4. Dans chaque carte de clé, ajoutez des valeurs avec Entrée, comme pour les variables.
  5. L'icône œil sur l'en-tête d'une carte bascule l'état actif de toute la clé ; l'icône œil sur une valeur bascule uniquement cette valeur. Désactiver une clé désactive ses valeurs en cascade (voir États actif / inactif).

Un HashMap se consomme ensuite dans un nœud pre_filter via filtre_source.

Guide d'utilisation — Mapping Audio & Image

Accessible via Données ▾ → Mapping Audio & Image.

  • Format Audio / Format Image — format de fichier global appliqué à toutes les ressources générées.
  • Régénérer — recalcule le mapping dossier pour chaque variable/HashMap : ajoute une entrée par défaut (dossier = nom) pour celles qui n'en ont pas, et retire les entrées obsolètes. Les mappings déjà personnalisés sont conservés.
  • Le tableau est en lecture seule ici : pour changer le dossier d'une variable, éditez audio_mappings directement dans le JSON, ou renommez la variable.
  • Switch à côté de chaque HashMap — active (par défaut) ou désactive la génération de ses propres ressources audio/image. À désactiver quand la clé et les valeurs du HashMap correspondent déjà à des variables existantes ailleurs dans le flow : le mobile réutilise alors leurs ressources, sans dupliquer les fichiers audio/image. Ce choix est stocké dans hashmaps_no_resources (liste des HashMaps exclus, tout le reste génère ses ressources par défaut) et retire immédiatement les entrées correspondantes du rapport de validation (audios et images).
Rappel Deux variables ne devraient jamais partager le même dossier de ressources — la validation le signale comme avertissement ("dossier partagé par plusieurs mappings").

Guide d'utilisation — Paramètres du Flow

Accessible via Données ▾ → Paramètres du Flow.

  • Nœud d'entrée (entry) — le nœud par lequel démarre le parcours (par défaut, le premier nœud du fichier).
  • Audio global :
    • Lire automatiquement la question (prompt) / les options — comportement par défaut de lecture audio dans l'app mobile.
    • Pause entre audios (ms) — silence entre deux éléments d'une séquence.
  • Langues — liste éditable : chaque langue apparaît comme une puce retirable ; tapez un nom (ex. mina) et cliquez sur Ajouter pour en créer une nouvelle (normalisée automatiquement en minuscules, sans doublon).
Attention Vider entièrement la liste des langues fait tomber à zéro le nombre de ressources audio attendues dans le rapport de validation (les images continuent d'être attendues normalement).

Guide d'utilisation — Import / Export / Nouveau projet

  • Auto-sauvegarde : chaque changement est automatiquement sauvegardé dans le stockage local du navigateur (localStorage) ; à la réouverture, le Studio restaure la session précédente.
  • Enregistrer : télécharge flow.json (format final, prêt pour le backend/Flutter).
  • Importer : charge un fichier JSON existant et reconstruit entièrement le graphe.
  • Nouveau : efface la session et repart d'un projet vide, avec toutes les valeurs par défaut (y compris les langues).

Guide d'utilisation — Validation du flow

Le bouton ✔ Valider ouvre un rapport structuré en plusieurs sections.

Erreurs bloquantes

  • audio_mappings manquant à la racine du JSON.
  • Objet audio manquant sur un nœud, ou audio.key manquant/dupliqué.
  • json_response_contrat ou un exemple de réponse qui n'est pas un JSON valide.
  • data_source.params contenant un nom vide, invalide ou dupliqué.
  • Une option ou un next qui pointe vers un identifiant de nœud inexistant.

Avertissements

  • Séquence audio vide ; nœud root sans option ; nœud de navigation sans next (cul-de-sac).
  • Nœud orphelin — jamais référencé par aucun autre nœud (sauf le point d'entrée).
  • Mapping ressource manquant pour une variable/HashMap ; deux mappings partageant le même dossier.
  • data_source.params vide (probable oubli) ; data_source.method non reconnue.
  • Un même endpoint utilisé avec plusieurs méthodes HTTP différentes selon les nœuds.
  • Boucle sans issue : un cycle du graphe dont aucun nœud n'atteint jamais un nœud result (une boucle qui possède une porte de sortie n'est jamais signalée).

Rapport d'inventaire automatique

Liste tous les audios/images référencés directement dans les nœuds, les variables utilisées, et le détail des ressources générées automatiquement (par variable, par HashMap) — exportable en JSON, Markdown ou HTML.

Contrat Backend

Tableau des routes dérivées des nœuds result, regroupées par (endpoint, méthode) : Méthode, Endpoint, Params (union de tous les nœuds qui partagent la route), Nœuds concernés — exportable en JSON ou Markdown. Se régénère entièrement à chaque clic sur Valider : aucune étape manuelle à refaire après avoir ajouté ou modifié une branche du flow.

Guide d'utilisation — Le Studio

Ouvert via le bouton ⬜ Studio, ce panneau regroupe trois onglets qui donnent au Studio un accès réel au disque (File System Access API).

Navigateur requis Ces trois onglets nécessitent Chrome, Edge ou Opera. Sur un navigateur non supporté (Firefox, Safari), un message bloquant s'affiche à la place — voir Compatibilité navigateur.

Une fois un dossier connecté dans un onglet, il reste mémorisé (avec redemande de permission au navigateur) pour les prochaines sessions et pour les autres onglets qui utilisent le même rôle de dossier (le dossier de ressources est partagé entre les trois onglets).

Onglet Ressources (Asset Repository)

  1. Connecter le dossier de ressources — choisissez le dossier racine contenant vos sous-dossiers audio/ et images/.
  2. Scanner — parcourt réellement le dossier, calcule un hash SHA-256 et la taille de chaque fichier trouvé sous audio/ ou images/ (tout le reste est ignoré).
  3. Le résultat affiche : le hash global du dépôt, le nombre de fichiers, la date de scan, le détail du manifest (chemin / taille / hash), puis la réconciliation :
    • Manquants — ressources attendues par le flow mais absentes du disque.
    • Orphelins — fichiers présents sur le disque mais non attendus par le flow.

Onglet Build

  1. Connectez le dossier de ressources (identique à l'onglet Ressources) et un dossier de sortie distinct (en écriture).
  2. Cliquez sur Lancer le Build.
  3. Le Build valide le flow, scanne les ressources, réconcilie les deux, dérive le contrat backend, puis écrit 8 fichiers dans le dossier de sortie (voir Fichiers générés).
Garde-fou Si le flow a des erreurs bloquantes, le diagnostic complet est quand même affiché (pour comprendre le problème), mais aucun fichier n'est écrit — jamais de sortie partielle ou incohérente sur disque.

Onglet Publication

Même moteur que le Build, avec une étape supplémentaire : la Publication copie en plus, dans {'{dossier de publication}'}/assets/, les seules ressources réellement référencées par le flow — jamais les fichiers orphelins, jamais un copier-coller aveugle de tout le dossier de ressources.

  1. Connectez le dossier de ressources et un dossier de publication distinct.
  2. Cliquez sur Publier.
  3. Le résultat indique le nombre de ressources copiées, en plus des mêmes diagnostics que le Build.

Le Build sert à vérifier/itérer en local ; la Publication produit le répertoire final, "propre", prêt à être livré au backend et à l'application Flutter.

Guide d'utilisation — Le Simulateur

Ouvert via le bouton 🚀 Simulateur, ce panneau rejoue le flow nœud par nœud, exactement comme le ferait l'application mobile Flutter : navigation interactive, lecture des vraies ressources audio/image, et test des routes API (réelles ou simulées). C'est l'outil de choix pour vérifier qu'un flow fonctionne réellement avant de le livrer.

Pourquoi un simulateur ? Il détecte automatiquement les chaînes de collecte cassées : si un paramètre attendu par un nœud result n'a jamais été collecté sur le chemin parcouru, le Simulateur l'affiche clairement plutôt que de laisser l'erreur invisible jusqu'à l'intégration mobile.

Configuration

Le bandeau en haut du panneau (repliable) rassemble tout ce dont le Simulateur a besoin :

  • URL de base du backend — préfixe ajouté devant l'endpoint de chaque nœud result.
  • Bearer Token — optionnel, envoyé en en-tête Authorization: Bearer ….
  • Langue — parmi les langues actives du flow ; détermine quel sous-dossier audio/{langue}/… est utilisé pour la lecture.
  • Dossier de ressources — le même dossier que l'onglet Studio → Ressources (voir Onglet Ressources) ; connectez-le pour activer la lecture audio/image réelle.

Cette configuration est mémorisée localement, indépendamment de la session du flow, et réutilisée à la prochaine ouverture.

Navigation

Chaque type de nœud propose l'interaction adaptée : options cliquables pour root/grid/pre_filter, sélecteur de date pour calendrier. La colonne latérale affiche le fil d'Ariane du chemin parcouru (chaque étape est cliquable pour revenir en arrière) et le contexte collecté en direct.

pre_filter avec liste vide Si la liste filtrée est vide (ex. un département sans marché dans le HashMap), le Simulateur l'affiche comme un avertissement explicite — c'est un signal de trou de données à corriger dans hashmaps, pas un bug du Simulateur.

Ressources audio & image

Une fois le dossier de ressources connecté, chaque option affiche un indicateur :

  • Vert — résolution canonique : chemin exact attendu, trouvé sur le disque.
  • Orange — résolution "au mieux" (voir ci-dessous), à vérifier.
  • Rouge — ressource introuvable.

Cliquer l'icône ▶ à côté d'une option joue son audio et affiche son image, sans sélectionner l'option (la sélection se fait en cliquant le reste du bouton). Les boutons Intro et Question en haut de chaque nœud jouent respectivement sa séquence audio d'introduction et son audio_prompt.

Résolution "au mieux" (hashmaps_no_resources) Pour un HashMap listé dans hashmaps_no_resources, aucun chemin canonique n'existe par construction (voir Mapping Audio & Image) : le Simulateur recherche alors le fichier par son seul nom dans tout le dossier de ressources — d'où l'indicateur orange, moins fiable qu'une résolution exacte.

Nœud résultat : appel API et repli simulé

  1. Le panneau latéral affiche un aperçu de la requête (méthode, URL, corps JSON) construite à partir du contexte collecté, avec les paramètres jamais collectés signalés en avertissement.
  2. Envoyer la requête tente le vrai appel HTTP. En cas d'échec (réseau, 4xx/5xx — le cas général tant qu'une route n'est pas développée), le Simulateur bascule automatiquement sur une réponse simulée, construite depuis response_examples ou json_response_contrat, avec les {placeholder} / {placeholder:défaut} remplacés par les valeurs collectées (ou leur valeur par défaut).
  3. Aperçu simulé prévisualise directement cette réponse simulée, sans tenter d'appel réel — utile tant qu'aucun backend n'existe encore.
  4. Si plusieurs response_examples existent, un menu déroulant permet de choisir lequel utiliser en repli.
  5. Si la réponse (réelle ou simulée) a la forme d'une enveloppe audio_sequence ({ type: "audio_sequence", sequence: [...] }), un bouton Lire la séquence joue chaque bloc dans l'ordre et affiche son image ; sinon, le JSON brut est affiché formaté.
Un bandeau distingue toujours réel et simulé Aucune ambiguïté n'est possible : une réponse réelle affiche son statut HTTP, une réponse simulée affiche systématiquement un bandeau "⚠️ Réponse simulée (route backend indisponible)".

FAQ & Dépannage

Le bouton Studio affiche "Navigateur non supporté"

Ouvrez le Studio depuis Chrome, Edge ou Opera. Firefox et Safari ne supportent pas encore l'accès réel au système de fichiers requis par ces fonctionnalités.

"Permission refusée pour ce dossier — reconnectez-le"

Le navigateur redemande une confirmation d'accès après chaque redémarrage, ou si la permission a expiré. Cliquez à nouveau sur le bouton de connexion du dossier concerné.

Le Build/la Publication n'écrit rien

Vérifiez la section "Erreurs Bloquantes" du résultat affiché : au moins une erreur de validation empêche toute écriture, par construction.

Le rapport de validation montre plus de ressources audio que prévu

C'est normal si plusieurs langues sont actives : chaque valeur de variable génère un fichier audio par langue, mais une seule image (jamais dupliquée par langue).

Une variable ne se supprime pas

Elle est encore utilisée dans un nœud (comme options_source ou set). Retirez d'abord ces références dans les nœuds concernés.

Je ne retrouve plus mon travail après un rechargement

Le Studio auto-sauvegarde dans le stockage local du navigateur (localStorage), propre à ce navigateur et cet appareil. Utilisez régulièrement Enregistrer pour exporter une copie flow.json durable.

Les boutons "Intro" / "Question" sont grisés dans le Simulateur

Le dossier de ressources n'est pas encore connecté (ou son scan a échoué) — connectez-le dans le bandeau Configuration du Simulateur, comme pour l'onglet Ressources du Studio.

"Envoyer la requête" tombe toujours en repli simulé

C'est attendu tant que la route backend n'est pas développée (voir les commentaires "⚠️ ROUTE BACKEND À DÉVELOPPER" dans flow.json). Le bandeau orange l'indique explicitement ; le statut HTTP ou le message d'erreur réseau reste affiché pour diagnostiquer.
